# Local training workflow

1. Download only BIOBUZZ footage confirmed as a fixed full-field camera. Do not use the listed holdout event footage for training.
2. Extract candidate frames with `python -m control_vision.training.extract_frames path\to\match.mp4 --output datasets\biobuzz-v1\images\unlabeled`.
3. Label boxes in CVAT and export YOLO format. Split whole matches, not adjacent frames, into `images/train`, `images/val`, `labels/train`, and `labels/val`. Prepare `split_manifest.csv` as described in [DATASET_SPLITS.md](DATASET_SPLITS.md), recording one row per labeled image with event/match identity, source, and rights. Reserve any `images/holdout` and `labels/holdout` for untouched evaluation. Copy `control_vision/config/data_biobuzz.example.yaml` to the dataset and adjust its path. An absolute `path` is safest; a relative path is rejected if it could name different datasets from the launch directory and the YAML directory. The training command passes the validated absolute path to Ultralytics. Use class order `robot`, `pollen`, `nectar`, or train only `robot` during the prototype.
4. Use a local base checkpoint (no model download is attempted): `python -m control_vision.training.train_yolo --data datasets\biobuzz-v1\data.yaml --base-weights models\yolo11n.pt --version 1.0.0 --device cpu`.
5. Before starting training, the command checks that the version is unused, every train/val image is readable and has a YOLO label file, boxes and class IDs are valid, the train split has labeled robots, and identical image files do not cross train/val. It also requires a valid match-level manifest by default. Empty label files are allowed for reviewed negative images. For an initial local experiment without a manifest, add `--exploratory-without-manifest`; the model metadata then says `exploratory_unverified` and is not evidence of a release-ready detector. A manifest cannot catch the same match entered under inconsistent IDs, so review its sources manually.
6. The script reserves the model version with an exclusive lock before training, records validation metrics, dataset SHA-256, and the split manifest SHA-256 or exploratory status, exports `models/yolo11n-biobuzz-v1.0.0.onnx`, and runs an ONNX Runtime CPU smoke check. Existing model versions are never overwritten. A crashed process can leave `models/.yolo11n-biobuzz-v<version>.lock`; remove it only after confirming no training run for that version is active.

The official BIOBUZZ Manual TU09 (Nov 12, 2026) describes POLLEN as yellow, about 2.8 inches, and NECTAR as red or blue, about 3.6 inches. The suggested class list is `robot`, `pollen`, and `nectar`; alliance color is a NECTAR attribute, not an extra class. The app uses class 0 (`robot`) for tracking. If classes 1 and 2 are present, changes in their detected count inside a user-drawn image-space ROI can create flagged review candidates. That count signal does not establish the scoring achievement, ownership, or robot attribution. Inspect the training log and model metadata; the utility does not establish holdout performance. Keep holdout events completely separate and report metrics with the specific matches used.
